# App idea 调研方法论 v2（美区 iOS · C 端 · 小团队）

日期：2026-10-27｜v1：`调研方法论-2026-10-27.md`｜简体中文。原则：不编造数字或引用，没核实的标「未核实」。
本版**不包含**「通用 AI 能否替代」这一判断项（按 Leon 要求）。

整体结构分两部分：
- **第一部分：判断用户提出的 idea 行不行**（需求 → 市场 → 竞品 → 细分人群 → 用户要完成的任务（JTBD）→ 赚钱逻辑 → 风险 → 结论）
- **第二部分：如果不行，同一领域里有哪些相似 idea 还有机会**（必须和用户 idea 属于同一领域）

## 名词小词典（先看这里）

读报告时遇到不懂的词，先查这张表。报告正文也尽量用大白话，非用不可的词第一次出现时会再解释一次。

| 术语 | 大白话意思 | App 小例子 |
|---|---|---|
| C 端 | 卖给普通个人用户，不是卖给公司 | 记账 App 卖给你自己用，就是 C 端 |
| MVP（最小可用版本） | 先做一个只有核心功能的简单版，拿去试水 | 减脂 App 第一版只做「按预算出一周菜单」，别的以后再加 |
| JTBD（用户要完成的任务） | 别问用户想要什么功能，问他在什么情况下想把什么事办成 | 用户「雇」健身 App 不是为了看数据，而是「夏天前瘦 5 斤，穿衣服好看」 |
| 四力 | 用户换用新 App 的拉锯：现状的烦恼、新东西的吸引在推他换；担心和懒得改习惯在拉他回来 | 想换记账 App，但怕旧数据导不过去、已经习惯了老的，最后还是没换 |
| 机会分数 | 给每个用户想要的结果打分：越重要、现在越不满意，分越高，越值得做 | 「快速找到今晚吃什么」很重要，但现有 App 都做不好 → 分高 |
| 变通办法 | 没有好产品时用户自己凑的土办法 | 用 Excel 记体重、用截图对比自己的脸 |
| 非消费者 | 有需求，但因为太贵、太麻烦，干脆什么都没用的人 | 想请私教但嫌贵，所以什么都不练的人 |
| 蓝海 / 红海 | 红海：很多大玩家抢的市场；蓝海：还没什么人做的新空间 | 记账 App 是红海；「专给 GLP-1 用户的饮食记录」可能更接近蓝海 |
| TAM / SAM / SOM（市场规模三层） | TAM：理论上所有可能的用户和钱；SAM：我们的产品真正能触达的那部分；SOM：小团队头一两年现实能拿到的那部分 | 全美想减肥的人是 TAM，其中用 iPhone、愿意用 App 的是 SAM，第一年能拉来的几千个付费用户是 SOM |
| 转化率 | 一步走到下一步的人占多少比例 | 100 人开始免费试用，37 人试用结束后付了钱 → 试用转付费率 37% |
| 付费墙 | App 里要求付钱才能继续用的那个页面 | 打开 App 先答问卷，然后弹出「7 天免费，之后每年 $59.99」 |
| 硬付费墙 / 免费增值 | 硬付费墙：不付钱基本用不了；免费增值：基础功能免费，高级功能收费 | 冥想 App 不订阅一节课都听不了 = 硬付费墙 |
| 留存 | 过一段时间后还在用（或还在付费）的人占多少 | 1 月订阅的 100 人，到 12 月还有 27 人在付钱 → 一年留存 27% |
| 续订率 | 订阅到期时，选择继续付钱的人占多少 | 月订阅第一个月到期，78 人里有 60 人续了 |
| ARPU / ARPPU | 平均每个用户 / 每个付费用户贡献多少钱 | 1000 个用户一个月共付 $500 → ARPU $0.5 |
| LTV（用户终身价值） | 一个用户从开始到离开，总共给你带来多少钱 | 用户每月付 $10，平均付 6 个月 → LTV 约 $60（还没扣苹果分成） |
| CAC（获客成本） | 拉来一个付费用户要花多少钱（主要是广告费） | 投 $1000 广告带来 20 个付费用户 → CAC $50 |
| LTV/CAC | 一个用户带来的钱是拉他花的钱的几倍；大于 1 才不亏 | LTV $60、CAC $20 → 3 倍 |
| 苹果分成 | 苹果从 App 内收费里抽成，常见 15% 或 30% | 用户付 $10，开发者到手约 $7–8.5 |
| ASO（应用商店优化） | 让 App 在 App Store 搜索里更容易被搜到 | 把「卡路里」放进 App 标题，让搜这个词的人看到你 |
| 关键词热度 | 苹果给的一个 1–5 分，表示这个词在 App Store 里有多少人搜，5 最热；不是具体搜索次数 | 「calorie counter」热度 5，「GLP-1 meal」可能只有 1–2 |
| 评分条数 | App Store 上给这个 App 打过分的人数；我们用它粗略判断 App 有多大 | 1 万条以上算大 App，1 千到 1 万算中等，1 千以下算小 |
| MAU（月活跃用户） | 一个月里至少打开过一次的用户数 | 某 App 月活 50 万 |
| PEST | 从政策、经济、社会、技术四个方面看外部环境对这个 idea 有什么影响 | 新减肥药流行（社会）、伊利诺伊州人脸隐私法（政策） |
| 波特五力 | 看一个行业好不好赚钱的五个角度：同行竞争、新人进来容不容易、有没有替代品、用户好不好说话、上游（平台）卡不卡你 | Spotify 不开放接口 = 上游卡脖子 |
| SWOT | 四格总结：我们的优势、劣势，外面的机会、威胁 | 优势：做得快；威胁：大 App 可能直接加这个功能 |
| Kano 模型 | 把功能分成：必须有的（没有就骂）、越好越满意的、意外惊喜的（没有也不会抱怨，所以用户不会主动提）、无所谓的 | 记账 App：数据不丢是必须有；自动识别小票是惊喜 |
| 价值主张画布 | 一张对照表：左边写用户要办的事、痛点、想要的好处，右边写我们的产品怎么一一对应解决 | 痛点「不知道吃啥」↔ 功能「每天推 3 个菜」 |
| 精益画布 | 一页纸写清楚生意怎么做：解决什么问题、给谁、怎么赚钱、花多少钱、靠什么获客 | 一页写完「减脂菜单 App」的商业计划 |
| 竞品功能矩阵 | 一张表，行是功能，列是竞品，打勾看谁有谁没有 | 一眼看出 5 个竞品都没有「按预算出菜单」 |
| 三角验证 | 至少两种不同来源的证据指向同一个结论才算数 | 竞品在赚钱 + 用户在用 Excel 凑合 → 需求可信 |
| 中位数 | 把所有数从小到大排，排在正中间的那个；比平均数更不容易被极端值带偏 | 5 个 App 月收入 $10、$50、$500、$800、$10万，中位数是 $500 |

## 第一部分：判断用户提出的 idea 行不行

每一步都写清楚：做法 → 数据源 → 产出表格 → 门槛。

### 第 0 步：拆解 idea
- **做法**：一句话写清「谁 + 在什么情境 + 想取得什么进展」；按人群、场景、技术、变现拆成 3–6 个子方向。不追问用户，先自己合理拆。
- **产出**：子方向表（子方向｜人群｜情境｜核心功能假设）。

### 第 1 步：需求判断（一种思维模式，不是固定规则）

社交平台上的用户原话**只是证据之一，不是圣经**。判断需求要回答的是：「这个缺口是否真实存在、够不够大、有没有人愿意为它付出（钱、时间、麻烦）」。证据可以来自市场，也可以来自方法论推理。

#### 1.1 证据类型与强度（由强到弱）

| 强度 | 证据类型 | 怎么看 | 数据源 |
|---|---|---|---|
| A 最强 | **市场验证**：已有相同或相似功能的产品，且有用户、有收入 | 评分条数（分档：1 万以上大、1 千以上中、以下小）、类目榜单排名、内购档位和订阅价格、最近更新是否活跃、下载/收入估算、网页流量 | iTunes Search/Lookup API、apps.apple.com、App Store 榜单、Sensor Tower/AppMagic（付费）、Similarweb、Appfigures |
| B 强 | **行为证据**：用户已经在为这个 Job 付出代价 | 自己凑的变通办法（Excel 模板、Notion 模板、备忘录、截图对比、拼好几个 App）、为替代品付费（线下服务、教练、实体产品）、搜索行为 | Google Trends、Apple Ads 关键词热度（1–5）、模板市场（如 Etsy、Notion 模板）、Reddit/X 里描述「我是怎么做的」的帖子 |
| C 中 | **相邻品类增长**：上下游或同一人群的相邻品类在涨 | 相邻 App 榜单上升、新药/新设备/新潮流的用户规模增长 | 榜单、Google Trends、行业报告、政府统计 |
| D 中弱 | **用户原话**：直接说出的痛点或愿望 | 原话 + 链接 + 日期 + 互动数；注意是谁在说、多少人附和 | X、Reddit、TikTok、App Store 差评 |
| E 推理 | **被创造的需求**：用户没说出来，但用有出处的方法论能推出缺口存在 | 见 1.2 | 方法论 + 上面各类证据做佐证 |

说明：强度排序是我的判断框架（经验），不是引用。差评属于 D 类，但它是**已付费或已安装用户**的原话，比泛泛的社交帖子更有分量。

#### 1.2 「被创造出来的需求」：用方法论推断缺口

用户说不出自己没见过的东西，但缺口可以被系统地推出来。每种推断都要写清「依据哪个方法论 + 哪些事实支撑」：

| 方法论 | 怎么用来发现隐性需求 | 出处 |
|---|---|---|
| JTBD：用户在「雇佣」什么 | 看用户现在雇佣什么来完成这个 Job（包括变通办法和「什么都不用」）。变通办法越笨重，说明未满足的需求越明确 | Re-Wired Group https://therewiredgroup.com/learn/complete-guide-jobs-to-be-done/ ；四力 https://jobstobedone.org/the-four-forces/ |
| 非消费（Christensen） | 找因为太贵、太麻烦、太复杂而**根本没在用**任何方案的人。非消费是指无法购买和使用某产品来完成重要的 Job；新市场颠覆针对的就是这些人，用更简单、更便宜、更易得的产品 | https://www.christenseninstitute.org/blog/the-importance-of-targeting-nonconsumption/ ；https://www.christenseninstitute.org/theory/disruptive-innovation/ ；六问 https://www.christenseninstitute.org/wp-content/uploads/2023/01/6-Questions-for-Disruptive-Innovation.pdf |
| 蓝海战略：四步动作框架 + 三层非顾客（Kim & Mauborgne） | 对现有竞品做 剔除/减少/增加/创造（ERRC）；分析三层非顾客：一层「准非顾客」勉强在用、等更好的；二层「拒绝型」看过但拒绝了；三层「未探索型」从没被当成目标用户 | https://www.blueoceanstrategy.com/tools/four-actions-framework/ ；https://www.blueoceanstrategy.com/tools/errc-grid/ ；https://www.blueoceanstrategy.com/tools/three-tiers-of-noncustomers/ |
| Kano 魅力属性 | 魅力属性具备时满意度大增，缺失时也不会引起不满，所以**用户不会主动提**。对照竞品找没人提供、但能明显提升体验的属性 | Kano 等 1984 原文 https://www.jstage.jst.go.jp/article/quality/14/2/14_KJ00002952366/_article ；五类定义 https://www.sensorysociety.org/knowledge/sspwiki/Pages/Kano%20Modeling%20in%20Product%20Development.aspx |
| 技术或环境变化 | 新药（如 GLP-1）、新法规、新 iOS 能力（端侧模型、新传感器 API）让以前做不到或不存在的需求出现。这类需求的特点是「新」，所以原话少很正常 | 来自 PEST 分析；每个变化都要附原始来源（FDA、Apple 开发者文档等） |
| 类比迁移 | 别的市场或品类已验证的模式（如「养宠打卡」从习惯类迁到戒酒类、某模式在网页端或别国已跑通）迁到本领域。被验证的是**模式**，不是本领域的需求，所以还要配一条本领域证据 | 作为分析习惯使用，无单一权威出处（未核实） |

#### 1.3 需求判断的思考框架：逐个回答的问题

1. **Job 是什么？** 谁，在什么情境下，想取得什么进展？
2. **现在用户雇佣什么来完成它？** 竞品、变通办法、付费替代品，还是什么都不用（非消费）？
3. **有没有市场验证？** 相同或相似产品的体量、收入信号、趋势如何？是在涨还是在衰退？
4. **有没有行为证据？** 用户是否在花钱、花时间、凑办法？搜索热度如何？
5. **用户自己说了什么？** 说的人是谁、有多少人附和，和沉默的大多数是否一致？
6. **如果用户没说，缺口靠什么推出来？** 套用 1.2 的哪个方法论，支撑的事实是什么？
7. **为什么现在？** 什么变化让这个需求现在可以被满足，或者现在才出现？
8. **反证是什么？** 有没有证据表明这个需求很小、是伪需求，或者已经被很好地满足了？

#### 1.4 三角验证：至少两类不同证据相互印证

规则：结论至少要有**两类不同**的证据（A–E 中的两类）相互印证；同一类证据再多也只算一类。下面是常见组合怎么判断（判断规则为经验框架）：

| 证据组合 | 判断 |
|---|---|
| A + B 或 A + D（市场有收入，且用户在用变通办法或在抱怨） | **需求已验证**，重点转向「现有方案哪里没做好」 |
| A 强但 D 几乎没有 | 需求仍成立（多数用户不发帖）；…2157 tokens truncated…济是算「拉来一个付费用户花多少钱，他一共能给我们多少钱」，后者要明显大于前者才不亏。

- **精益画布**：问题、细分、独特价值主张、解决方案、渠道、收入、成本、关键指标、壁垒。
- **单位经济**：
  - 定价：参考同类竞品内购档位（apps.apple.com 页面）和 Adapty 全球中位价（周 $7.48 / 月 $12.99 / 年 $38.42）。
  - 转化：RevenueCat 分类目、分试用时长的基准（例：试用→付费中位数 5–9 天 37.4%）；Adapty 安装→试用 10.9%、试用→付费 25.6%。
  - LTV（一个用户总共带来的钱）≈ 每个付费用户每月付的钱（ARPPU）× 扣掉苹果 15%/30% 分成后的比例 × 平均付费月数；CAC（拉来一个付费用户的广告费）用 Apple Ads 或 TikTok 广告估算（我们拿不到真实的单次安装成本 CPI，标「假设」）。例：每月 $10、平均付 6 个月、扣 15% → LTV 约 $51；广告花 $17 拉来一个 → LTV/CAC 约 3。
  - 获客渠道：有没有自然传播点（分享卡片、前后对比）、ASO 关键词热度。
- **产出**：精益画布；单位经济表（指标｜取值｜来源｜已核实/假设）。
- **门槛**：LTV/CAC ≥ 3（一个用户带来的钱是拉他花的钱的 3 倍以上）是行业常用经验线（本轮未核实出处）；没有付费意愿证据时最多 ★★½。

### 第 8 步：优劣势总结与风险（SWOT）

大白话：SWOT 是四格总结，我们的优势、劣势，外面的机会、威胁。

- **SWOT**：基于上面所有步骤，优势/劣势是「我们做这个」，机会/威胁来自 PEST、五力和竞品。
- **风险清单**：技术、合规、平台政策、留存（奖励/内容一周耗尽）、获客。
- **产出**：SWOT 四格；风险表（风险｜可能性｜影响｜MVP 怎么规避）。

### 第 9 步：结论
- 结论先行：**行 / 有条件行 / 不行**，加星级和综合分（见下方评分卡）。
- 写清推理链：证据 → JTBD 机会 → 竞品空白 → 细分 → 商业可行 → 风险。
- 行的话：给 MVP 范围、首个验证实验（如落地页 + Apple Ads 小预算测点击/预约）。
- 不行的话：写明卡在哪一步，进入第二部分。

## 第二部分：同一领域里还有哪些相似 idea 有机会

**硬约束**：相似 idea 必须和用户 idea 属于**同一领域**（同一个大 Job 或同一个用户群的相邻 Job），不能跳到别的赛道。

### 怎么系统地找（5 个入口）
1. **沿 Job 地图找**：把用户 idea 的大 Job 拆成步骤（定义 → 准备 → 执行 → 监控 → 调整 → 结束，ODI 的 job map 思路）。用户 idea 只覆盖其中一步，其他步骤里机会分高的就是候选。
2. **沿细分人群找**：同一个 Job，换一个第 6 步里「证据有、服务弱」的人群（如 GLP-1 用户、新手、预算有限者）。
3. **沿差评找**：大竞品差评里反复出现、没人解决的问题，单独做成一个聚焦 App。
4. **沿新变化找**：PEST 里的新药、新法规、新 iOS 能力、新潮流在本领域带来的新需求。
5. **沿四力找**：用户卡在「焦虑」或「习惯」上时，降低焦虑/切换成本本身就是一个产品（例如公平对比、可撤销、免登录）。

### 怎么快速评估（同一标准的精简版）
每个候选只做 4 件事：
1. **需求快检**：用第 1 步的证据类型（A–E）做三角验证，至少两类证据相互印证（经验值），例如相似产品的体量 + 变通办法/差评，或技术变化 + 方法论推断。写一句「需求属于：已验证 / 潜在 / 新需求」。
2. **竞品快检**：iTunes Search 3–5 个关键词，分档，套机会矩阵。
3. **差评快检**：头部 1–2 个竞品的 1–3 星评论，有没有本候选针对的问题。
4. **商业快检**：同类竞品有没有在卖订阅；关键词热度 1–5。
然后用下方评分卡打分，排序给出 2–5 个。

### 产出
候选对比表（idea｜和原 idea 的关系｜Job 步骤/人群｜证据类型组合｜竞品状态｜机会矩阵结论｜得分｜星级）+ 每个入选 idea 的简版卡片（标题、目标用户、痛点证据、竞品空白、MVP、变现、风险）。

## 三、评分卡与星级

| 维度 | 权重 | 5 分标准 | 1 分标准 |
|---|---|---|---|
| 需求证据（三角验证） | 25% | A 类市场验证 + 至少一类其他证据相互印证 | 只有推测或只有零散原话 |
| JTBD 机会分 | 15% | 有结果机会分 ≥ 12 | 全部 < 10 |
| 竞品空白（机会矩阵） | 20% | 「有机会」或「新需求可以做」 | 「没有机会」或「旧需求空白」 |
| 市场规模与趋势 | 10% | SOM 足够、趋势上升 | 太小或下滑 |
| 付费意愿与单位经济 | 15% | 竞品订阅卖得动、用户说愿付 | 无付费证据 |
| 可做性（小团队 1–3 月 MVP） | 10% | 现成 API/端侧能力即可 | 需重研发或数据壁垒 |
| 风险（合规/平台/留存） | 5% | 无硬伤 | MVP 绕不开的硬伤 |

（权重为我设定的经验值，可调。任何「硬否决」项直接判不行，不看总分。）

| 加权得分 | 星级 | 含义 |
|---|---|---|
| ≥ 4.2 | ★★★★ 以上 | 建议立即做 |
| 3.5–4.1 | ★★★ | 做 MVP 验证，先排除 1–2 个风险 |
| 3.0–3.4 | ★★½ | 有机会，但证据偏弱或障碍明显 |
| 2.5–2.9 | ★★ | 暂不建议，等变化 |
| < 2.5 | ★ 以下 | 放弃 |

**硬否决信号**：需求只是推测、没有任何方法论和事实支撑；红海且痛点已被大 App 解决；空白但旧需求；平台政策禁止；合规风险 MVP 绕不开；留存只靠新鲜感。

## 五、报告写作原则
- **给用户的报告少用术语**：能用大白话就不用术语；必须用时，第一次出现先用一句话解释并举一个 App 小例子（参考开头的「名词小词典」）。
- **每个指标都要说清楚**：它是什么意思、数字高或低分别代表什么、和同类比算高还是低。例：「试用转付费率 37%：100 个试用的人里有 37 个付了钱，同类 App 的中位数约 37.4%，属于正常水平」。
- 不编造数字或引用；估算、假设、未核实分别标明。
- 先判断需求，后分析竞品（竞品体量本身也是需求证据）；每个推荐写出推理过程。
- 结论先行，标题清晰。
- 报告存 `/workspace/appidea-vault/research/<主题>-YYYY-MM-DD.md`。
